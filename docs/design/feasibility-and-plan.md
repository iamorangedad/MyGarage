# MyGarage - 可行性分析与架构设计

## 可行性分析

### 结论
**可行，但需要分层架构：MuJoCo 负责"机械物理"层，上层需要"故障逻辑模型"。**

### 参考项目分析
项目 [microduck](https://github.com/pollen-robotics/microduck) 的架构思路值得借鉴：
- 主体是 Rust 编写的机器人运行时（控制循环、舵机总线、蓝牙、OTA 更新）
- MuJoCo 部分位于 [microduck_rl](https://github.com/pollen-robotics/microduck_rl) 和 `scripts/duck-sim`
- 核心思想：**真实逻辑和"身体"分离**，同一套接口既能接真机也能接 MuJoCo 里的模型
- 采用 MJCF 一个部件一个部件拼装模型的方式，对应"一个零件一个零件积累"的开发策略

### MuJoCo 的能力边界

#### 擅长的部分（刚体动力学）
- 悬挂系统
- 刹车卡钳
- 轮毂轴承
- 转向拉杆
- 皮带轮
- 曲柄连杆机构
- **能表现的故障类型**：异响、抖动、旷量、卡滞等机械故障

#### 不擅长的部分
MuJoCo 不直接模拟：
- 电路
- 燃烧过程
- 油液压力
- 温度
- 声音

因此，以下系统需要单独的**系统模型层**（状态机 + 信号计算）：
- 电瓶
- 点火系统
- 喷油系统
- 传感器
- 故障码

系统模型层驱动 MuJoCo 的表现，例如：点火缺缸 → 曲轴力矩不均匀 → MuJoCo 表现出抖动。

## 系统架构

### 分层设计

```
┌─────────────────────────────────────────┐
│          用户界面层 (UI Layer)           │
│  Python + MuJoCo Viewer / ImGui / Web   │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│        游戏逻辑层 (Game Logic)           │
│  故障注入、诊断流程、评分、任务管理       │
└─────────────────┬───────────────────────┘
                  │
      ┌───────────┴───────────┐
      │                       │
┌─────▼──────────┐   ┌───────▼────────────┐
│  系统模型层     │   │   部件层           │
│ (System Model)  │◄──│ (Component Layer)  │
│                 │   │                    │
│ 电气/燃油/      │   │ MJCF 模型          │
│ 点火/传感器     │   │ 正常参数           │
│ 状态机          │   │ 故障模式           │
└─────┬──────────┘   │ 诊断读数映射       │
      │              └────────────────────┘
      │
┌─────▼──────────┐
│   MuJoCo 层     │
│ 物理仿真引擎    │
│ MJCF 场景       │
└────────────────┘
```

### 1. 部件层 (Component Layer)

**设计原则**：每个零件是独立的可插拔模块。

每个部件模块包含：
- **MJCF 模型**：几何体、质量、关节、传动
- **正常参数**：额定值、容差范围
- **故障模式**：可能出现的故障及其参数变化
- **诊断读数映射**：各诊断工具测量时的读数计算

**添加新部件的流程**：
1. 在 `src/mygarage/components/` 下创建新模块
2. 实现 `Component` 接口
3. 在 `data/faults/` 添加该部件的故障条目
4. 无需修改核心代码

### 2. 系统模型层 (System Model Layer)

负责电气、燃油、点火等非机械系统的行为。

**功能**：
- 维护系统状态（电压、电流、温度、压力等）
- 根据故障调整参数
- 驱动 MuJoCo 中的执行器（如起动机扭矩）
- 生成传感器读数

**示例**：
- 点火系统：缺缸 → 曲轴力矩不均 → MuJoCo 表现抖动
- 起动机系统：电瓶电压 → 起动机转速 → 曲轴转动

### 3. 故障引擎 (Fault Engine)

**数据驱动设计**：故障库采用 YAML 格式。

每个故障条目包含：
- **ID** 和 **名称**
- **涉及的部件**
- **根本原因**
- **症状描述**（客户抱怨）
- **可观测的测试结果**
- **修复方法**
- **难度等级**

**工作流程**：
1. 从故障库随机抽取故障
2. 将故障注入到车辆系统
3. 生成症状描述给玩家
4. 记录正确的根本原因用于评分

### 4. 诊断工具系统 (Diagnostic Tools)

提供抽象的诊断动作，而非真实物理操作：

- **目视检查**：观察部件外观、连接状态
- **OBD 扫描仪**：读取故障码、数据流
- **万用表**：测量电压、电阻、电流
- **油压表**：测量油路压力
- **晃动测试**：检测机械旷量
- **起动测试**：尝试启动并观察

**交互方式**：
- 玩家选择工具
- 玩家选择测点
- 系统返回读数（基于当前故障状态）

### 5. 维修与评分系统

**玩家动作**：
- 使用诊断工具获取读数
- 更换零件（记录成本）
- 提交诊断结论

**评分维度**：
- ✓ 是否找到根本原因
- ✓ 诊断步骤数（越少越好）
- ✓ 更换零件的成本（不必要的更换扣分）
- ✓ 时间（可选）

### 6. 用户界面

**第一版（v0）**：
- Python + MuJoCo 自带查看器显示 3D 场景
- 终端文字界面或 ImGui 面板显示信息和控制
- **必须支持无头模式**（headless/CLI），用于测试和自动化

**未来扩展**：
- 基于浏览器的 MuJoCo WebAssembly 版本
- 完整的 GUI（PyQt/Tkinter 或 Web）

**核心逻辑与 UI 解耦**：所有游戏逻辑不依赖特定 UI，便于替换前端。

## 第一个示例：12V 电瓶 + 起动机系统

### 选择原因
- **偏电气系统**：验证系统模型层的设计
- **故障丰富且真实**：常见且易理解
- **诊断步骤明确**：适合作为教学示例

### 包含的部件

1. **12V 蓄电池**
2. **起动机（含电磁开关）**
3. **曲轴**（最小化表示）
4. **点火开关**
5. **保险丝/继电器**
6. **接地线束**

### 故障模式示例

| 故障 ID | 名称           | 症状                       | 关键诊断读数                    |
|---------|----------------|----------------------------|---------------------------------|
| F001    | 电瓶亏电       | 起动无力或无反应           | 静态电压 <12V，负载下 <9V       |
| F002    | 电瓶单格损坏   | 起动无力，电压快速下降     | 静态 12V+，负载下降至 8V        |
| F003    | 电瓶桩头腐蚀   | 间歇性无法起动，有咔哒声   | 电压正常，桩头处压降 >0.5V      |
| F004    | 接地线松动     | 起动无力或无反应           | 正极电压正常，负极压降 >0.5V    |
| F005    | 起动机电磁开关故障 | 只有咔哒声，不转动    | 电压正常，电磁开关线圈断路      |
| F006    | 起动机磨损     | 转动缓慢，异响             | 电流过大，转速低                |
| F007    | 保险丝熔断     | 完全无反应                 | 保险丝前有电，后无电            |
| F008    | 继电器失效     | 无反应或仅咔哒声           | 继电器控制信号正常，主触点开路  |

### 可观测的测量

- **静态电池电压**
- **起动时电池电压**（负载电压）
- **电压降测试**（桩头、接地线）
- **起动电流**
- **起动机转速**（通过曲轴角速度）
- **声音反馈**（咔哒声、正常转动、异响）
- **目视检查**（腐蚀、松动、烧蚀）

## 主要风险与应对

### 风险 1：3D 模型复杂度
- **应对**：前期使用简单几何体（长方体、圆柱体）
- 功能验证优先，美术资产后置

### 风险 2：物理交互的实现难度
- **问题**：在 MuJoCo 中真实拧螺丝、拆装零件很困难
- **应对**：拆装、测量做成**抽象动作**
  - 物理仿真只负责**表现症状**
  - 玩家通过菜单/命令选择动作

### 风险 3：故障库质量
- **关键**：故障的真实性决定训练价值
- **应对**：
  - 结合用户实际维修经验编写
  - 参考维修手册和案例
  - 逐步迭代和扩充

### 风险 4：MuJoCo 与系统模型的同步
- **应对**：明确接口定义，系统模型输出作为 MuJoCo 执行器输入
- 定义清晰的数据流

### 核心接口

#### Component 接口
```python
class Component:
    def get_mjcf_model(self) -> str:
        """返回 MJCF XML 字符串"""
    
    def apply_fault(self, fault_id: str):
        """应用故障到部件"""
    
    def get_diagnostic_reading(self, tool: str, params: dict) -> dict:
        """返回诊断工具的读数"""
```

#### DiagnosticTool 接口
```python
class DiagnosticTool:
    def measure(self, target: str, params: dict) -> dict:
        """执行测量，返回读数"""
```

#### SystemModel 接口
```python
class SystemModel:
    def update(self, dt: float):
        """更新系统状态"""
    
    def get_actuator_commands(self) -> dict:
        """返回 MuJoCo 执行器的控制信号"""
```

## 总结

MyGarage 项目通过 **MuJoCo 物理仿真 + 系统逻辑模型** 的分层架构，可以实现：
- 真实的机械故障表现（MuJoCo）
- 完整的电气、燃油系统行为（系统模型）
- 数据驱动的故障库（YAML）
- 模块化的部件系统（易于扩展）
- 抽象的诊断流程（避免复杂物理交互）
- 有效的训练评分（诊断能力评估）

第一版聚焦于 **电瓶 + 起动机系统**，验证整体架构的可行性。核心逻辑与 UI 解耦，支持无头测试，为未来扩展到 Web 平台打下基础。
